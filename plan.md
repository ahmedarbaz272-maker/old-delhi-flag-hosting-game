# Implementation Plan — Gyanu: The Flag Hosting Mission

## Scope and source materials

Deliver the supplied Three.js/TypeScript/Vite browser game as a static, no-account, single-player experience. The approved Game Blueprint keeps server, database, multiplayer, and online services off. Preserve the existing initialized Three.js/Rapier starter, its fixed-step engine, input, physics, camera, save, quality settings, localization, and game-owned Tweak adapter; replace its Sky Cores gameplay with the requested city mission rather than replacing the starter. The public corporate repository is unrelated, so publish from the separate `AuraKareSollutions/old-delhi-flag-hosting-game` repository created for this game.

Inspected Drive materials: `IMG_9348.jpeg` is a Delhi overview map; `IMG_9349.png` is a 16-panel city/landmark collage; `IMG_9350.png` is the assembly-ground reference; the supplied `gyanu` image is a 2350×1824 transparent PNG and must be used byte-for-byte as the flag artwork; `PRD Gyanu — The Flag Hosting Mission.docx` supplements the attachment with controls, mission-state, save, accessibility, and acceptance details. Use the references to guide original geometry and spatial composition, not to reproduce an actual city map or unlicensed game art.

## Gameplay and implementation approach

1. **Mission/state layer:** define the 16 named locations in one data file, a versioned local save, a single mission state, and explicit objective/flag-hosting transitions. The final-area unlock is gated by all 16 location completions; the only victory state is `HOSTED` after an on-platform, in-range interaction.
2. **World:** create a compact connected walkable city with alley/market/district clusters, open plazas, city edge, skyline, and a separate secured assembly ground. Use a repeatable architectural kit plus selected detailed 3D assets for focal buildings and characters. Keep world coordinates, spawn points, patrol routes, and objective regions in configuration. Use Rapier static collision helpers aligned with visible barriers/buildings, and real stairs/landing for the tower.
3. **Player and input:** extend the starter input/action map and Rapier character controller for walk, sprint, crouch, jump, interact, pause, map, and camera switch; reuse the engine's keyboard/gamepad/touch adapters and same simulation state. Add an FPP mode and retain a collision-aware third-person follow mode. Touch controls must prevent page scrolling.
4. **Crowds/security:** use bounded reusable NPCs with visible idle/walk/join/follow/formation states and simple obstacle recovery. Security uses configurable waypoint patrols and distance/FOV/line-of-sight checks, then suspicion, pursuit, search/detention, failure, and a reliable restart. Keep NPC work staggered and browser-friendly.
5. **Final objective:** model secured-area barricades, tower, visible climbable stairs, top platform and pole as actual 3D geometry. Load exact user flag from `public/assets/flags/gyanu.png`, keep its aspect ratio/transparency, animate raising, and show victory once. Holding interaction is cancellable; detention cancels it.
6. **UI and persistence:** menus, briefing, HUD, map, pause, settings, controls, failure, and victory remain accessible HTML/CSS UI. Preserve the starter's English/Simplified Chinese locale switch and matching catalogs; persist mission progress safely and keep settings under the existing save owner. Include readable prompts, keyboard focus, reduced motion and touch-safe layouts.
7. **Assets:** follow the approved hybrid workflow and use the user's explicit Manus-credit approval for the four generated GLBs already created: runner, gatherer, guard, and bazaar building. Catalog access did not bind to this project, so use these registered models plus original procedural city geometry rather than claiming catalog reuse. No additional credit spend is authorized under this plan. Keep generated audio out of scope absent separate approval. Retain asset notices/provenance and a license inventory; show fallbacks when a registered model cannot load.
8. **Release:** build as a static Vite site. Set the Vite base for `/old-delhi-flag-hosting-game/`, add an Actions workflow for GitHub Pages, preserve the user's existing company repo/site, and verify build/output paths before enabling public Pages. Use a game-specific title/favicon and complete sharing preparation under the current WebDev workflow; publish only after a clean build and confirmed checkpoint/deploy result.

## Visual design

- **Design movement:** colorful, polished arcade-runner 3D presentation, specifically requested as “Subway Surfers type graphics,” interpreted as detailed, vivid, readable 3D buildings and characters rather than copied art, characters, logo, maps, or assets.
- **Core principles:** saturated but readable color blocks; distinctive layered facades and sculpted rooflines; detailed generated characters supported by lightweight crowd movement; strong wayfinding between objective hubs.
- **Color philosophy:** warm terracotta/sandstone and sunlit cream distinguish the old-city architecture; teal/cyan, saffron/gold, and coral accents identify routes, markers, and crowd feedback; security/readiness states use shapes and labels as well as color.
- **Layout paradigm:** connected street-and-plaza geography with short sightline reveals, distinctive landmark nodes, broad player routes, and a deliberate open assembly ground at the end; the HUD remains edge-anchored and touch-safe.
- **Signature elements:** original generated 3D player, gatherer and security characters; a textured bazaar frontage plus a reusable architectural kit; painted façade bands/awning clusters; bright objective rings and pennants; expressive animated people; the supplied flag on the tower's actual pole.
- **Interaction and animation:** responsive, forgiving controls; clear prompt radius; gentle settle, bob, follow, cloth-wave, alert-pulse, and success-rise motions; reduced-motion option controls decorative effects.
- **Typography:** bundled starter faces, with a compact bold display treatment for objectives and neutral readable body text; never embed essential text in generated textures.
- **Brand essence and voice:** a lively, original city mission about gathering allies and raising the supplied banner; spirited, warm, adventurous. Microcopy stays short and specific, e.g. “Gather the square” and “Reach the tower platform.”
- **Wordmark and signature color:** create an original title lockup from a custom geometric pennant/arch motif (not a derivative of Subway Surfers branding); use vivid teal as the primary game accent.

## Project structure

Keep the starter `src/engine/` and `src/main.ts` integration intact. Add focused modules under `src/game/` for mission state, location data, city construction, NPC/crowd/security behavior, flag hosting, map and collision, and adapt existing `world.ts`, `player.ts`, `camera.ts`, `game.ts`, and config. Retain `src/ui/` for menu/HUD/touch additions; update `src/styles/main.css` and `src/i18n/en.json` (plus matching keys in the existing second catalog). Place exact flag and model assets under `public/assets/` and source/runtime-registered models under `assets/` per the approved WebDev asset lifecycle. Add focused tests under `tests/`, a manual/automated test report under `docs/`, and a static Pages workflow under `.github/workflows/` in the GitHub delivery copy.

## Delivery constraints

No mandatory backend, account, multiplayer, paid API, audio-generation consent, or modifications to the unrelated company-site repository. Do not say the request is complete until the production build and GitHub Pages publication are verified. Document remaining limits if the playable scope has to be staged.
